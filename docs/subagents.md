# Субагенты разработки Work Search

Набор учитывает текущие границы проекта: Electron main/preload, React UI, доменную очередь, аудиозахват, Whisper, два AI-транспорта и зашифрованную SQLite. Главный агент собирает результат и отвечает за интеграцию. Специалисты получают ограниченные задачи и конкретные файлы.

## Каталог

| Имя | Когда использовать | Основные файлы | Результат |
| --- | --- | --- | --- |
| `architect` | Новая функция затрагивает несколько слоев; нужна декомпозиция или оценка совместимости | Чтение `src/`, `docs/architecture.md`, контрактов | План, контракты, зависимости и задания; без правок |
| `backend` | Очередь, начало/завершение интервью, отмена, ревизии, восстановление, метрики | `src/domain/`, `src/application/` | Измененная бизнес-логика и проверки через порты |
| `frontend` | Оверлей, настройки, история, потоковый ответ, CSS и доступность | `src/renderer/` | Рабочий React UI с состояниями загрузки/ошибок и проверкой поведения |
| `electron` | IPC, preload, окна, трей, горячие клавиши, Windows-жизненный цикл | `src/main/`, `src/preload/index.ts`, `src/shared/ipc.ts` | Согласованный IPC и desktop-поведение |
| `ai_integrations` | Cloud WebSocket, local Codex RPC, отмена, reconnect, streaming, профили и AI latency | `src/adapters/ai/`, `service-integration/`, `scripts/benchmark-providers.mjs` | Надежный транспорт с корректным восстановлением и проверками |
| `audio_stt` | Микрофон, системный звук, AudioWorklet, Whisper, CPU/память и скорость STT | `src/capture/`, `src/preload/capture.ts`, audio/STT adapters, `scripts/setup-whisper.ps1` | Исправленный аудиопайплайн, освобождение ресурсов, измерения по fixtures |
| `storage` | История, схема БД, миграции, шифрование, outbox и диагностика | `src/adapters/storage/` | Совместимое хранение с проверкой сохранности данных |
| `qa` | Воспроизведение регрессии, тестирование нескольких слоев, подготовка приемки | `tests/`, `e2e/`, тестовые конфиги, `docs/acceptance.md` | Тесты, результаты прогонов и явные ограничения |
| `reviewer` | Независимая проверка готового изменения перед завершением | Чтение назначенного изменения и вызывающих путей | Подтвержденные ошибки, риски и пробелы проверок; без правок |
| `release` | Зависимости, native ABI, сборка Windows x64, упаковка и NSIS | Конфигурации проекта, runtime/installer/smoke scripts | Проверенная сборка или пакет в объеме задания |

`frontend` совмещает реализацию UI и работу с доступностью; отдельный дизайнер для текущего размера приложения не требуется. Задержкой занимаются владельцы соответствующего этапа — `backend`, `ai_integrations` или `audio_stt`. Полный код внешнего backend-сервиса здесь отсутствует: `ai_integrations` работает с имеющимися клиентом и скриптами интеграции.

## Файлы и загрузка

Определения находятся в [`.codex/agents/`](../.codex/agents/). Каждый TOML содержит `name`, `description` и `developer_instructions`; `architect` и `reviewer` дополнительно задают `sandbox_mode = "read-only"`. Это проектные custom agents по [официальному формату Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents).

[`.codex/config.toml`](../.codex/config.toml) включает агентов и ограничивает число одновременно открытых дочерних потоков тремя. Это предел одновременной работы, а не числа доступных ролей. Модели и effort не закреплены: используется выбор родительской сессии. Исполнительные роли также наследуют ее разрешения. Файловые области в инструкциях — правила координации, не отдельные ограничения файловой системы.

[Корневой AGENTS.md](../AGENTS.md) содержит общую архитектуру, маршрутизацию задач, правила владения файлами и матрицу проверок. Он дополняет TOML-определения. Модель и профиль AI-помощника внутри самого Work Search задаются кодом приложения и его настройками отдельно.

После добавления файлов открой новый чат Codex в корне этого проекта и назови нужные роли в запросе. Если клиент не видит роли, проверь поддержку проектных TOML-агентов в его версии и загрузку конфигурации проекта. Новые файлы не означают, что агенты уже запущены в текущем чате.

## Skills ролей

К каждой роли подключены проектные процедуры из [`.agents/skills/`](../.agents/skills/). Основные навыки указаны непосредственно в `developer_instructions` TOML-агента, общая маршрутизация — в AGENTS.md. Полный список, назначение и примеры вызова: [docs/skills.md](skills.md).

Backend использует `work-search-feature`, frontend — `work-search-react-ui`, electron — `work-search-electron-ipc`, AI — `work-search-ai-recovery`, audio/STT — `work-search-audio-stt`, storage — `work-search-sqlite`, QA — `work-search-testing`, release — `work-search-release`. Архитектор использует анализ сквозного сценария; reviewer — критерии профильного skill и оценку проверок. Они сохраняют режим чтения.

Навыки обнаруживаются стандартным механизмом Codex; дополнительных внешних сервисов для их загрузки не нужно. Автоматический выбор включен по умолчанию, но загружаются только навыки текущей задачи.

## Примеры запросов

Новая функция через несколько слоев:

> Добавь экспорт выбранного интервью в Markdown. Сначала поручи architect определить контракт и файлы. Затем используй backend, electron и frontend по их областям. Пусть один исполнитель меняет каждый общий контракт, qa проверит сценарии, а reviewer проверит готовое изменение. Дождись результатов и проверь интеграцию.

Исправление интерфейса:

> Используй frontend: исправь потерю несохраненных настроек при обновлении snapshot. Сохрани текущий DesktopApi. Добавь проверку наблюдаемого поведения в e2e/ui-renderer.spec.ts и запусти ее после сборки.

Проблема восстановления:

> Используй ai_integrations для воспроизведения повторной генерации после reconnect. backend подключи, если причина в очереди; storage — если нарушена атомарность outbox. Сначала установи причину, затем исправь ее и проверь отсутствие повторной отправки.

Аудио и производительность:

> Используй audio_stt: найди причину задержки распознавания двух дорожек. Сравни одинаковые RU/EN fixtures до и после изменения, сохрани качество текста и отдельно укажи время STT. Используй доступную локальную модель.

Независимое ревью:

> Поручи reviewer проверить назначенные изменения на гонки отмены, потерю истории и утечки данных. qa пусть независимо оценит пробелы тестов. На этом этапе исходники не меняй; дождись обоих отчетов и объедини подтвержденные замечания.

Сборка:

> Используй release: подготовь Windows x64 пакет и проверь packaged smoke в отдельном профиле. Согласуй Node/Electron ABI и запиши результаты, путь артефакта и оставшиеся проверки на чистой Windows.

## Передача задачи и интеграция

В задании исполнителю указываются:

```text
Роль: frontend
Цель: сохранить черновик настроек при обновлении snapshot.
Можно менять: src/renderer/Settings.tsx, e2e/ui-renderer.spec.ts.
Контракт: существующие AppSnapshot и DesktopApi.
Приемка: новый snapshot обновляет статусы, но не затирает редактируемые поля;
         неизмененный токен не отправляется повторно.
Проверки: typecheck, затем build и выбранный browser E2E.
Координация: тестовый файл закреплен за frontend;
             build/E2E запускаются после завершения остальных правок renderer.
Отчет: поведение, файлы, команды и результаты, ограничения.
```

Чтение можно выполнять параллельно. Для записи назначается один владелец каждого файла; это касается и тестов. Если нужен новый IPC или формат хранения, сначала согласуется контракт, затем реализуются зависимые части. Главный агент проверяет их совместимость после завершения исполнителей.

`pnpm test` не запускает тесты service-integration; им нужна отдельная команда `node --test`. SQLite Vitest требует Node ABI, Electron — Electron ABI. Подробная последовательность, opt-in native-проверки и условия доступа к реальным сервисам находятся в [AGENTS.md](../AGENTS.md).

Для небольшой задачи достаточно одной роли. Для сквозного изменения обычно подходят архитектор перед реализацией, два-три исполнителя по слоям, затем QA и ревью. Все десять ролей одновременно запускать не нужно.
