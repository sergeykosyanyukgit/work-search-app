# Локальный Codex и облачный codex-manager — 0.1.4

В «Подключении» доступны два провайдера. По умолчанию выбран облачный, включая обновление с 0.1.3. Настройки применяются к следующему интервью; текущий провайдер виден отдельно в настройках и истории. Локальный режим использует уже установленный нативный Windows `codex.exe` с авторизацией ChatGPT. Модель продолжает выполняться через Codex в облаке, интернет необходим. CLI, Docker, WSL и Node не устанавливаются вместе с приложением.

Пустой путь означает поиск в PATH и каталогах Windows Codex; каталог сборки определяется заново, без закреплённого хеша. Можно выбрать exe вручную. «Проверить подключение» получает версию, account/read и model/list. Требуются ChatGPT-вход и выбранная модель с effort=low. Начальная модель `gpt-5.6-sol`, стандартная скорость; автоматической замены модели нет. При отсутствии входа выполняется `codex login` через установленный CLI. Приложение не вызывает logout и не меняет config.toml.

Изменённый путь к CLI применяется при явном продолжении/восстановлении локального интервью, сохраняя его модель. Это позволяет заменить удалённый или несовместимый executable без потери истории.

## Процесс и транспорт

Контракт проверен на `codex-cli 0.154.0-alpha.6.2`, на основе сгенерированных этой версией типов и [официальной документации App Server](https://learn.chatgpt.com/docs/app-server). Используется ограниченная Zod-схема необходимых сообщений. Несовместимый CLI вызывает понятную ошибку. WebSocket App Server остаётся экспериментальным протоколом: совместимость с будущими версиями требует повторной проверки.

Main запускает собственный скрытый процесс в `userData/codex-workspace`. Он слушает только `127.0.0.1` на случайном свободном порту. На каждый запуск создаётся 256-битный ключ; CLI получает только SHA256 через `--ws-auth capability-token --ws-token-sha256`. Сам ключ передаётся в Authorization при установлении WebSocket и не сохраняется. До initialize выполняется отрицательная проверка соединения без ключа: если CLI её допускает, процесс закрывается.

Параметры собственного процесса отключают shell/unified exec, Code Mode, приложения, plugins, hooks, memories, multi-agent, browser/computer use, image/view tools, goals, sleep и поиск host skills. Для каждого унаследованного MCP-сервера thread config задаёт enabled=false. Read-only sandbox, approvalPolicy=never, web_search=disabled; входящие запросы инструментов и пользовательских подтверждений отклоняются. Инструкции повторяют interview-assistant@2. Глобальные настройки/авторизация сохраняются. Эти настройки не являются универсальной гарантией отсутствия любых новых инструментов в будущих Codex runtime.

Во время интервью процесс прогрет, после пяти минут бездействия выгружается. Завершение приложения и смена интервью закрывают только созданное этим экземпляром дерево процессов по его PID через taskkill /T. Нет завершения по имени процесса. stderr/stdout CLI не журналируются.

## Доставка и восстановление

Перед turn/start зашифрованный outbox сохраняет неизменяемые параметры, request ID и question ID. request ID передаётся в `clientUserMessageId`; это корреляция, не обещание идемпотентности. Принятый turn ID сохраняется у вопроса. native `userMessage.clientId` проверен после завершения процесса: он позволяет найти запрос даже при потере подтверждения.

При явном продолжении вызываются thread/resume, thread/turns/list и thread/items/list с пагинацией. Терминальный результат сохраняется без генерации. Активный подтверждённый turn ожидается в существующем thread; повторный turn/start не отправляется. До сверки outbox очередь остановлена. Если история не подтверждает доставку, вопрос сохраняет частичный ответ и становится interrupted; очередь требует явного ручного повтора этого вопроса или нового интервью. Обрыв транспорта не объявляется успешной отменой.

В 0.154 подтверждение turn/start может опередить возможность turn/interrupt и первую запись rollout. При быстрой отмене известная ошибка «no active turn to interrupt» проверяется повторно в ограниченном интервале; временно пустая история перечитывается. Outbox удаляется только после терминального состояния. Эта гонка воспроизведена и проверена на нативном Windows CLI.

Если thread удалён, приложение предлагает «Продолжить подключение». После этого создаётся новый thread и сбрасывается contextSent; следующий prompt включает профиль и последние 20 завершённых пар в пределах 32 000 символов. У ожидающих запросов удалённого thread требуется ручной повтор. Автоматического переключения на другой провайдер нет.

Промежуточный ответ хранится как Map блоков по item ID. Native дельты собираются только внутри блока, полные снимки заменяют блок. Повторные полные события не удваивают текст. Native поток не имеет облачного sequence/cursor: после обрыва используется история, а не предположение о replay дельт. reasoning, планы и служебные сообщения исключены. Итог перечитывается из элементов завершённого turn; таймаут генерации — 120 секунд.

## Хранение и диагностика

Миграция SQLite user_version 1→2 выполняется одной транзакцией: старые настройки, интервью и команды получают provider=cloud, ID/cursor/payload/секреты сохраняются. Содержимое SQLite по-прежнему шифруется safeStorage. Локальный thread создаётся persistent: дополнительная копия текста сохраняется в собственной истории Codex. Удаление интервью из приложения не удаляет эту копию; это поясняется в настройках и подтверждении удаления.

Диагностика добавляет provider, локальную модель и CLI version к прежним длительностям. Сырые конфигурации, ответы RPC, исключения CLI, токен и текст интервью в лог не выводятся. Проверка настроек создаёт отдельный короткий транспорт. Локальная проверка не создаёт thread. Облачная проверка создаёт/закрывает пустую служебную серверную сессию без turn/start и без записи интервью в приложении.

## Воспроизводимые проверки

```powershell
pnpm typecheck
pnpm test
$env:RUN_LOCAL_CODEX='1'
pnpm exec vitest run tests/local-codex.native.test.ts
Remove-Item Env:RUN_LOCAL_CODEX
pnpm build
pnpm test:e2e
pnpm dist
pnpm test:packaged
node scripts/benchmark-providers.mjs --run
```

Native-тест использует текущую авторизацию и один синтетический вопрос. Он проверяет защищённый WS, каталог/вход, генерацию, durable client ID и восстановление после закрытия процесса. В истории Codex остаётся интервью с явным названием проверки.

Benchmark запускает упакованное приложение в отдельном профиле, копирует только зашифрованный облачный токен в main из существующего профиля Windows и использует пять одинаковых коротких вопросов в обоих режимах. Реальное резюме и историю интервью не копирует. Отчёт содержит только длительности и технические метки. Данные: [providers-windows-0.1.4.json](benchmarks/providers-windows-0.1.4.json). Первый запрос и последующие сравниваются отдельно; STT исключён из этих замеров. Отдельная проверка на чистой Windows и матрица программ захвата не заменяются этим тестом.
