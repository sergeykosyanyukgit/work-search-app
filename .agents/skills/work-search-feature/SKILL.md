# Изменение сценария интервью

Прочитай [архитектуру](../../../docs/architecture.md) и [общие правила](../../../AGENTS.md). Для анализа или ревью выполни только чтение и проектирование; реализация зависит от назначенной роли и задачи.

## Проследи сценарий

Определи входную команду в `src/shared/ipc.ts`, обработчик `src/main/index.ts`, метод `src/application/interview-controller.ts` и используемый порт из `src/domain/ports.ts`. Найди UI-потребителей `AppSnapshot` и сохраненные поля в `src/domain/types.ts`. Для сквозного изменения запиши, какие из этих контрактов действительно меняются, и назначь одного владельца каждого общего файла.

Зафиксируй начальное состояние, действие, ожидаемый переход, запись в хранилище и видимое состояние UI. `review` и `interrupted` входят в `TERMINAL_STATUSES`, но наличие durable outbox может отдельно удерживать доставку: не выводи возможность повторной отправки только из статуса вопроса.

## Проверь влияющие переходы

- Первый ручной вопрос и первая запись могут создавать интервью. Изменения не должны требовать заранее нажать отдельную кнопку создания.
- Резерв очереди появляется до доступа к устройствам. В `nextAiQuestion` следующий готовый текст не обходит более раннюю запись/STT.
- В `pump` STT и AI независимы; отмена, смена интервью и shutdown должны завершать задачи так, чтобы поздний callback не обновил новое интервью.
- При восстановлении `ensureConnection` может уже найти завершенный вопрос. Перед `send` проверь обновленное сохраненное состояние, а не старый объект.
- Проверка подключения и восстановление интервью — разные операции. Не связывай сохранение настроек с запуском генерации.
- Если меняется prompt/context, проверь первую отправку и продолжение старого интервью; ревизия сохраняет исходную запись через `revisionOf`.

Выбери только затронутые переходы; не расширяй изменение до всех перечисленных сценариев.

## Реализуй и проверь

Начни с минимального контракта, затем адаптеров/use case и UI. Для ошибки очереди используй fake-порты и `tests/helpers/memory-store.ts`; управляй завершением promises и сравнивай порядок фактических вызовов порта и сохраненные вопросы.

Команды: `pnpm typecheck`, затем выбранные `tests/domain.test.ts`, `tests/controller-start.test.ts`, `tests/controller-recovery.test.ts` через `pnpm exec vitest run`. При изменении схемы, IPC или UI подключи соответствующий проектный skill по таблице в AGENTS.md. Отчет должен показывать новый переход состояния и его проверку.
