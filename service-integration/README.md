# Подготовка Codex Manager

Каталог `codex-manager` содержит два аддитивных файла для соседнего репозитория. `apply-to-codex-manager.ps1` копирует только эти файлы и отказывается перезаписывать отличающиеся существующие файлы. Он не запускает серверные операции и не меняет package.json.

Путь к отдельно полученному репозиторию сервера задавайте явно:

```powershell
.\service-integration\apply-to-codex-manager.ps1 -Repository 'C:\path\to\codex-manager'
```

Текущая версия скрипта публикует `interview-assistant@2`. Перед применением обновите manager и worker до реализации постоянного Codex App Server, а frontend — для отображения аналитики. Для работы V2 worker должен понимать поля профиля `codex_manager_runtime: app-server` и `codex_manager_base_instructions`; при передаче upstream-конфигурации эти служебные поля удаляются. Копирование двух скриптов само по себе не обновляет исполняемый код сервиса. Инструкции V2 встроены в профиль и не требуют файла prompt из соседнего репозитория или машины разработчика.

Проверка после копирования:

```powershell
node --test scripts/provision-interview-assistant.test.mjs
```

Администратор передаёт `CODEX_MANAGER_ADMIN_TOKEN` через окружение процесса и задаёт точный model ID. Скрипт обновляет снимки моделей/квот READY workers и проверяет наличие выбранной модели. Предпросмотр:

Даже без `--apply` скрипт выполняет внешний `POST quota/refresh` для READY workers. Это не read-only dry run. Локальная проверка без обращения к сервису — отдельный `node --test`, приведённый выше.

```powershell
node scripts/provision-interview-assistant.mjs --model MODEL_ID
```

Применение и отдельная явная выдача нового клиентского ключа:

```powershell
node scripts/provision-interview-assistant.mjs --model MODEL_ID --apply
node scripts/provision-interview-assistant.mjs --model MODEL_ID --apply --issue-key
```

Только `--issue-key` выводит новый клиентский токен. Повторное применение не создаёт ключи и не меняет чужих клиентов. По умолчанию скрипт находит или создаёт клиента с `externalId=work-search-app`. Новому клиенту задается `queueTimeoutMs=30000`; все квоты существующего клиента, включая время ожидания очереди, сохраняются. Профиль `interview-assistant@2` неизменяем: дрейф требует новой версии каталога. Каждая мутация проходит через существующие admin API и audit сервиса. Ключ получает только `sessions:read`, `sessions:write`; desktop никогда не получает admin token.

При наличии V1 скрипт создает и публикует V2, сохраняя содержимое V1; публикация снимает с V1 флаг `published`. На пустом каталоге API последовательно создает неопубликованную каноническую V1 и опубликованную V2. Совпадающая V2 повторно не создается, более новые версии не понижаются. Новые сессии с профилем `interview-assistant` без номера получают опубликованную версию, а открытые интервью сохраняют снимок своей конфигурации. Для перехода на V2 начните новое интервью.

V2 использует одну явно выбранную модель, `reasoningEffort: low`, `model_verbosity: low`, `model_reasoning_summary: none` и прежний лимит 24 000 токенов. По умолчанию запрашивается прямой ответ на 20–35 слов и до двух опорных пунктов. Явные просьбы о подробностях или коде поддерживаются. Быстрый платный режим и автоматический перебор моделей не включаются.

Если токен уже выпущен для отдельного клиента приложения с другим именем или без `externalId`, укажите его точный ID из `GET /api/v1/admin/clients`. Например, клиент `work-search` может быть подготовлен без создания второго клиента:

```powershell
node scripts/provision-interview-assistant.mjs --model MODEL_ID --client-id EXISTING_CLIENT_ID
node scripts/provision-interview-assistant.mjs --model MODEL_ID --client-id EXISTING_CLIENT_ID --apply
```

В этом режиме сохраняются имя, `externalId`, все квоты (включая время ожидания очереди) и существующие ключи. Скрипт меняет только разрешения выбранного клиента для профиля интервью. Клиент должен быть активен, запрещать direct config и иметь пустой список разрешённых профилей либо только `interview-assistant`. Неизвестный ID, неактивный клиент и клиент с другими профилями приводят к отказу без изменения профилей или клиентов. Новый ключ и здесь выдаётся только отдельным `--issue-key`.

Ошибка `Profile is not allowed by client policy` означает, что профиль запрещён политикой владельца текущего токена. Создать профиль на сервере недостаточно: подготовьте именно этого клиента. После изменения политики переподключите приложение (или перезапустите его), поскольку WebSocket использует политику, прочитанную при подключении. Сам manager перезапускать не требуется.

Историческая проверка V1: 11 сентября 2026 на `https://api.code-manager.ru` опубликован `interview-assistant@1` с единственной моделью `gpt-5.6-sol` и `reasoningEffort: low`. Подготовлен существующий выделенный клиент; его прежний токен и квоты сохранены. Повторная подготовка подтвердила отсутствие изменений. Проверка публичного WebSocket прошла полный цикл `session.open` → `turn.start` с `originator: chatgpt` → `turn.completed` → `session.close`; непустой ответ получен за 6,2 секунды. Отдельный временный проверочный ключ отозван после теста. Для повторной сверки используйте ID собственного клиента: `--model gpt-5.6-sol --client-id EXISTING_CLIENT_ID`.

После обновления сервиса 11 сентября 2026 опубликована V2 с той же `gpt-5.6-sol` и `low`. Ключи и квоты клиента `work-search` сохранены; повторная подготовка не внесла изменений. Это обновление профиля и runtime; исходный замер V1 выше остается отдельным результатом. Определения первого текста и полного ответа, а также новые измерения приведены в [документации задержки](../docs/latency.md).

Профиль запрещает сеть, web search, MCP, overrides, direct config и запись в sandbox. Флаги отключают shell, unified exec, apps, multi-agent и view_image. `read-only` само по себе не запрещает инструменты. Эффективный набор инструментов зависит от используемого Codex 0.145.0: отдельные флаги и инструкция в prompt не являются универсальной гарантией `tool_choice=none`. Скрипт задает выбор runtime через профиль; обновление контейнера worker выполняется отдельно.

Выбирается единственная проверенная модель: текущий manager не реализует настоящий fallback modelSequence. При истечении серверной сессии desktop создаёт новую и передаёт локальный контекст; локальная история хранится независимо от серверного retention. Неопределённо принятый запрос не переносится автоматически в другую сессию.
